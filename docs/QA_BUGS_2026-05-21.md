## P0 / #15 — `availableToBorrow` goes negative for past asOf dates

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_15_available_to_borrow_consistent_as_of` (`tests/Feature/QaBugs20260520Test.php:621-660`).
- **Assertion:** `availableToBorrow($asOf)` where `$asOf` is **before any OWN** is funded must be `≥ 0`.
- **Actual:** returns **`-500`**.
- **Smoking gun (test failure message):**
  > "The calculator is subtracting *current* active-CL outstanding from *past* OWN."
- **Likely fix site:** the as-of helper that backs the loans-summary "available
  to borrow" tile (look for `availableToBorrow` / equivalent on `AccountExt`
  or `CreditLineService`). The fix is to compute the outstanding at `$asOf`,
  not at `now()`.
- **Blast radius:** any historical report / loans-summary view past the CL
  origination date is wrong. Customers viewing pre-CL snapshots see negative
  available-to-borrow.

## P0 / #16 — `as_of` account view renders future credit-line state

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_16_as_of_view_hides_future_credit_line_state` (`tests/Feature/QaBugs20260520Test.php:662-695`).
- **Assertion:** rendered HTML for an `as_of` view dated **before** the CL's
  `origination_date` must not contain `Net outstanding ... 1,000.0000`.
- **Actual:** the present-day `Net outstanding 1,000.0000` is rendered on the
  past-dated page.
- **Likely fix site:** loans-summary partial (or its Livewire wrapper)
  doesn't filter CLs by `origination_date <= $asOf`. Likely the same data
  source that backs #15 — fix once, both close.
- **Blast radius:** historical / audit views show data that didn't exist at
  that point in time. Combined with #15, the as-of view is structurally
  unreliable.

## P0 / #17 — TWR shifts when BOR + REP zero-value transactions exist

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_17_twr_excludes_bor_rep_transactions` (`tests/Feature/QaBugs20260520Test.php:700-730`).
- **Assertion:** Time-weighted return computed on an account with **no**
  borrow activity (cleanTwr) must equal TWR on the same account after a
  paired `BOR + REP` (both `value = 0`).
- **Actual:** `cleanTwr = -10` → `withBorrowTwr = -8.65`. 1.35 point drift.
- **Likely fix site:** `AccountExt::periodPerformance($from, $to)` (or
  whatever it forwards to). The cash-flow series almost certainly treats
  BOR/REP shares as a positive/negative cash flow even though their
  `value = 0` (shares were lent, not bought/sold). Filter `type IN
  ('BOR','REP')` out of the TWR cash-flow input.
- **Blast radius:** every customer-facing performance number for an account
  that has ever opened a CL is wrong. The bigger the BOR/REP ratio to the
  underlying OWN, the larger the drift.

## P0 / #7 — Loans summary "Lifetime repaid" tile is 50 when the truth is 150

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_07_loans_summary_tiles_reconcile_with_cl_row_totals` (`tests/Feature/QaBugs20260520Test.php:318-396`).
- **Assertion:** `Lifetime repaid` tile must equal `SUM(principal − outstanding)`
  summed across CLs (the authoritative "shares actually repaid") **not**
  `SUM(transactions WHERE type=REP)` (which is corruptible by the
  still-open overpay path documented as QA-05-20#1).
- **Actual:** tile = `50.0`, expected `150.0`.
- **Likely fix site:** the loans-summary-card composer / view-model
  (`LoansSummaryBuilder` per coverage report — `App\Services\CreditLine\Reporting\LoansSummaryBuilder`).
  Switch the "Lifetime repaid" source from raw REP sum to per-CL
  `principal − outstanding`.
- **Cross-ref:** this is a follow-on of QA-05-20#1 ("Overpayment silently
  absorbs the excess"). The overpay fix is separate; this tile fix is
  independent and worth shipping standalone since it stops the *display*
  from disagreeing with itself.

## P1 / #20 — `/credit-lines/{id}` 500s when the CL account is soft-deleted

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_20_cl_show_handles_soft_deleted_account` (`tests/Feature/QaBugs20260520Test.php:822-845`).
- **Assertion:** GET `/credit-lines/{id}` must not return HTTP 500 when the
  CL's `account` row has `deleted_at != NULL`.
- **Actual:** HTTP 500.
- **Likely fix site:** `CreditLineController@show` (or its repository) eager-
  loads the account with the default scope, then accesses a column on `null`.
  Either use `withTrashed()` in the eager load or short-circuit to a 404
  with a flash explaining the parent account is archived.
- **Severity rationale:** rare in practice (deleted accounts shouldn't have
  active CL URLs being clicked), but a 500 leaks the stack trace in dev and
  drops the user with no recovery path.

## P1 / #19 — `/api/transactions` omits `account_credit_line_id` on BOR rows

- **Test:** `Tests\Feature\QaBugs20260520Test::test_bug_19_transactions_api_includes_credit_line_id` (`tests/Feature/QaBugs20260520Test.php:791-817`).
- **Assertion:** for a BOR transaction returned by `/api/transactions`, the
  JSON row must have key `account_credit_line_id` so the UI can link the
  row back to the originating CL.
- **Actual:** key is missing from the array.
- **Likely fix site:** `App\Http\Resources\TransactionResource` (or the
  API repository's `toArray` projection) — add `account_credit_line_id` to
  the field allow-list. It already lives on `transactions.account_credit_line_id`
  (set by the BOR write path); just expose it.

## P2 / #14 — `QaTestUsersSeeder` writes non-existent `accounts.type` column

- **Test:** `Tests\Feature\QaBugs20260519Test::test_bug_14_claude_test_user_is_role_assigned_after_seeders` (`tests/Feature/QaBugs20260519Test.php:372`).
- **Error:** `SQLSTATE[42S22]: Column not found: 1054 Unknown column 'type'
  in 'INSERT INTO' (... insert into 'accounts' ... 'type' ...)`.
- **Fix site:** `database/seeders/QaTestUsersSeeder.php:70`. The seeder
  sets `'type' => 'individual'` on `AccountExt::firstOrCreate`, but
  `Schema::getColumnListing('accounts')` returns no `type` column. Either
  (a) drop the `type` key from the seeder, or (b) add the missing migration
  if the prod DB was hand-altered to have it. Inspect prod schema before
  choosing.
- **Why P2:** the affected test is the only thing that runs the seeder
  inside `RefreshDatabase`. Real-user impact is "QA beneficiary fixture
  silently absent in fresh dev envs" — annoying, not load-bearing.

## P2 / #bb1 — testpool baseline is stale, misses one migration

- **Not a test failure per se** — the migration `2026_05_19_000004_create_credit_line_delay_notifications_table`
  is in `database/migrations/` but not in `database/test/test-baseline.sql.gz`.
- **Symptom:** fresh `testpool.sh claim` produces a slot DB with no
  `credit_line_delay_notifications` table; 7 tests (4 × `ScanJobsTest`,
  3 × `S9DelayNotificationDedupTest`) error out until you manually
  `docker exec familyfund-<slot> php artisan migrate --force`.
- **Fix:** in a slot with migrations applied + DB in a known-good shape,
  run `~/.familyfund-pool/testpool.sh snapshot dev` (or `snapshot test2`
  after this run), then `git add database/test/test-baseline.sql.gz` and
  commit. The skill knows how.
- **Why P2:** the test pool is a developer-facing tool; current devs all
  know to run `migrate --force`. New / CI users wouldn't.
