## Working hypothesis (one root cause, ~21 of 22 failures)

Every test that fills a form and presses submit hits the same shape:

1. The form **renders correctly** — screenshot `04_create_form_filled.png`
   from `CreditLineUITourTest` shows all 7 inputs populated, the
   "Available to borrow as of 2026-05-21: 4111.0336 shares" hint visible,
   and the "Open" button enabled.
2. The test calls `->press('Open')` (or equivalent).
3. The page **never redirects** to `/credit-lines/{id}`; Dusk waits 10 s,
   times out, and the test fails with `TimeoutException`.
4. No follow-up screenshot is captured (the assertion fired before the next
   `->screenshot()` call), so the post-press state is invisible — but the
   one place we *did* see post-press state
   (`S9LateNotificationSmokeTest`) shows the submit button is
   `disabled=""` and another element is intercepting the click.

The shared root cause is therefore most likely **the submit handler doesn't
fire / the form action is interrupted by client-side validation**, not 21
distinct backend bugs. Likely candidates:

- A recent change to the credit-line create / repay forms introduced a
  client-side disabled-until-valid gate (matches `d8afb7fb fix(ui):
  credit-line create form over-borrow warning + empty-state` and
  `d1c87884 feat(credit-line): single Make payment button + Fill remainders
  allocate UX` in `git log`), and Dusk's `->type()` / `->select()` calls
  don't trigger the `input`/`change` events the gate listens for.
- Stale Vite assets in the slot image — the `testpool.sh claim` flow doesn't
  rebuild `public/build/*` against the worktree's `resources/` tree, so the
  compiled JS in the container can be from an older asset bundle (the warm
  cache from another branch).
- A `wire:` / Livewire payload that Dusk isn't waiting on before pressing
  submit.

This is **one investigation** to start, not 22.

  `->dump()` call immediately after the `->press('Open')` in

  the form-request rules likely need adjusting, OR the controller's redirect
  target is wrong after recent allocation-ledger changes.

## P1 / #ui-2 — Submit button disabled + overlap on S9

- **Test:** `Tests\Browser\Scenarios\S9LateNotificationSmokeTest::loan_share_show_renders_late_state_for_backdated_line`
  (`tests/Browser/Scenarios/S9LateNotificationSmokeTest.php:75`).

- **Smoking gun (exception):**
  > `ElementClickInterceptedException: Element <button type="submit"
  > class="btn btn-primary" id="submit-btn" disabled="">...</button> is not
  > clickable at point (61, 873). Other element would receive the click:
  > <form method="POST" action="http://familyfund-test1:8000/accounts/7/credit-lines">...</form>`

- **Two separable problems:**
  1. The submit button is `disabled=""` at the moment Dusk clicks it, so a
     human user with JS enabled would also see a non-clickable submit until
     some client-side condition is met. The test, written against a
     previously-passing UI, doesn't wait for that condition.
  2. The `<form>` itself is *on top of* the button at the click point, so
     even if the button were enabled, the click would target the form
     element. This is a CSS / layout regression (z-index or stacking-context
     change) on the credit-line create form.

- **Blast radius:** any human user who tries to submit the
  `/accounts/{id}/credit-lines` create form while the JS validity gate is
  still pending will see the button visually present but unresponsive.
  Worse, if (2) is real for human users (not just Selenium), the click is
  silently swallowed by the form.

- **Suggested investigation:** load `/accounts/7/credit-lines/create` in a
  real browser, fill the form, and check (a) when the submit button enables
  (which `input`/`change` event), and (b) whether DevTools "elements at
  point" on the submit button shows the form intercepting.

## P2 / #ui-bb1 — `tour` skill hardcodes credit-line filter

- **Where:** `~/.familyfund-pool/testpool.sh::cmd_tour()`, line ~450:
  ```bash
  local args=("$@"); [ ${#args[@]} -eq 0 ] && args=(--filter=CreditLineUITourTest)
  ```

- **Effect:** running `testpool.sh tour test1` with no args silently filters
  to one test class. Running `testpool.sh tour test1 -- tests/Browser/` does
  pass through and runs the whole suite, but the helper text in the
  [`test-env` skill](../) doesn't document this. A reviewer following the
  skill at face value would only ever see 1/27 of the Dusk picture.

- **Fix:** either drop the default filter (so a no-arg invocation runs
  everything), or document the pass-through pattern in the skill's "Run
  Dusk UI tours" section so the reader doesn't have to read the bash to
  discover it.
