## Working hypothesis (one root cause, ~21 of 22 failures)

Every test that fills a form and presses submit hits the same shape:

1. The form **renders correctly** — screenshot `04_create_form_filled.png`
   from `CreditLineUITourTest` shows all 7 inputs populated, the
   "Available to borrow as of 2026-05-21: 4111.0336 shares" hint visible,
   and the "Open" button enabled.
2. The test calls `->press('Open')` (or equivalent).
3. The page **never redirects** to `/credit-lines/{id}`; Dusk waits 10 s,
   times out, and the test fails with `TimeoutException`.
4. No follow-up screenshot is captured (the assertion fired before the next
   `->screenshot()` call), so the post-press state is invisible — but the
   one place we *did* see post-press state
   (`S9LateNotificationSmokeTest`) shows the submit button is
   `disabled=""` and another element is intercepting the click.

The shared root cause is therefore most likely **the submit handler doesn't
fire / the form action is interrupted by client-side validation**, not 21
distinct backend bugs. Likely candidates:

- A recent change to the credit-line create / repay forms introduced a
  client-side disabled-until-valid gate (matches `d8afb7fb fix(ui):
  credit-line create form over-borrow warning + empty-state` and
  `d1c87884 feat(credit-line): single Make payment button + Fill remainders
  allocate UX` in `git log`), and Dusk's `->type()` / `->select()` calls
  don't trigger the `input`/`change` events the gate listens for.
- Stale Vite assets in the slot image — the `testpool.sh claim` flow doesn't
  rebuild `public/build/*` against the worktree's `resources/` tree, so the
  compiled JS in the container can be from an older asset bundle (the warm
  cache from another branch).
- A `wire:` / Livewire payload that Dusk isn't waiting on before pressing
  submit.

This is **one investigation** to start, not 22.

## P0 / #ui-1 — Form submit via Dusk never redirects

**✅ Closed in test code.** Root cause was a recent backend addition the
tests hadn't been updated for: `e62d7465 wip(credit-line): nickname +
effective-date migrations` added `nickname` as both an HTML5 `required`
input on `account_credit_lines/create.blade.php:50` AND a
`required|string|max:255` rule in `CreateAccountCreditLineRequest.php:22`.
None of the Dusk tests that drove this form ever typed into the nickname
field — Chrome's native form validation silently aborted the submit when
`->press('Open')` fired, so the URL never changed and Dusk waited the full
10 s.

The screenshot evidence was right there: `04_create_form_filled.png` shows
the nickname field with only its placeholder text (`e.g. Kitchen renovation
loan`) while every other field is populated. The "Open" button being
visually enabled was a red herring — HTML5 doesn't disable the submit
button, it just refuses to POST.

**Fix (commit landing on `main` with this update):** add
`->type('input[name="nickname"]', '<label>')` to the form-fill sequence in
every offending test. 9 files touched:

- `tests/Browser/CreditLineAllocateUITest.php`
- `tests/Browser/CreditLineBorrowingFlowTest.php`
- `tests/Browser/CreditLineNegativeUITest.php` (4 sites)
- `tests/Browser/CreditLineSimulatorUITest.php` (2 sites)
- `tests/Browser/CreditLineUITourTest.php`

- `tests/Browser/Scenarios/S9LateNotificationSmokeTest.php`

**Result of fix:** Dusk now reports **14 passed / 13 failed** (was 5 / 22).

## P1 / #ui-2 — Submit button disabled + overlap on S9

**✅ Closed in test code.** Originally read as "two separable problems"
(button disabled AND form overlapping the click) — one root cause, not two:

- The test was using
  `$browser->clear('input[name="origination_date"]')->type('input[name="origination_date"]', '2026-04-21')`
  to backdate the origination by 30 days.
- Chrome's native `<input type="date">` doesn't take a single string into
  its `value` from keyboard input — `->type()` enters characters one at a
  time into the **month / day / year segments**. The intended `2026-04-21`
  was parsed as month `20`, day `26`, year `0421` (visible in the failure
  screenshot:
  `tests/Browser/screenshots/failure-Tests_Browser_Scenarios_S9LateNotificationSmokeTest_test_loan_share_show_renders_late_state_for_backdated_line-0.png`,
  where the date control reads `02/02/0421` and the "Available to borrow as
  of 0421-02-02" hint shows `0.0000 shares`).
- The form's JS (`create.blade.php:174-181`) on `change` of the date input
  ran `fetchAvailable()` against the bogus past date `0421-02-02`, got
  `available=0`, and `syncOverBorrow()` set `submitBtn.disabled = true`.
- `$browser->press('Open')` then tried to click a disabled button — Chrome
  reported `ElementClickInterceptedException` with the parent `<form>` as
  the recipient.

**Fix:** set the date via JS rather than typing into the date input:

```php
$browser->script(
    "var el = document.querySelector('input[name=\"origination_date\"]');"
    . "el.value = '" . $originationDate . "';"
    . "el.dispatchEvent(new Event('change', {bubbles:true}));"
);
```

This is the standard Selenium pattern for HTML5 `<input type="date">`.
`dispatchEvent` is required so the form's `change` listener still runs
`syncWarning()` + `fetchAvailable()` and the page re-renders the warning
and the (now correct) available-to-borrow figure.

**Result of fix:** S9 now drives past the form successfully, creates the
backdated CL, and reaches the show-page assertions. New failure is at
line 47 — `assertSeeIn('table.table', 'Late')` — tracked separately as
#ui-7.

This was **not a CSS / overlay bug**. The "form intercepts click" message
is what Chrome emits any time the click target is disabled; the parent
form just happens to be the next element in the stacking context.

## P1 / #ui-7 — S9 schedule table missing "Late" label

**✅ Closed in test code.** Two issues compounded:

1. **Backdate too short.** A 30-day backdated origination produces a
   monthly schedule whose **first** payment is due ~1 month after
   origination — i.e. due today. Today is inside the 3-day default
   grace, so `DrawService::detectForLine` (which runs synchronously at
   create — confirmed at `DrawService.php:117`) doesn't flag any row
   yet. With 90 days of backdating, the first 2–3 rows are well past
   grace and get flagged correctly. Verified via tinker — the latest
   CL's schedule shows rows `2026-03-20 late / 2026-04-20 late /
   2026-05-20 late / ...` in `credit_line_payments`.
2. **Case mismatch.** The pill is rendered by
   `account_credit_lines/_payment_status_badge.blade.php:11` as
   `<span class="badge bg-danger">late</span>` — lowercase. The
   assertion `assertSeeIn('table.table', 'Late')` (capital L) didn't
   match.

Also widened the selector from `table.table` → `table` (the rendered
table on the show page doesn't carry the `.table` CSS class anyway).
Test now passes (4 assertions).
